App Routing

Route different apps through different lines: bind your browser, games and download tools to suitable lines, each independent of the others.

The page subtitle says it: route different apps through different lines. The "Enable App Routing" master switch sits at the top, off by default, with an "Add app binding" button above the table. The master switch gates this whole page — bindings you add below only take effect once it's on. Each binding connects one app to one or more lines, after which that app's traffic follows the bound lines.

The binding table

All bindings are listed in a table, one binding rule per row.

ColumnMeaning
AppShows the icon and name / process name.
Target linesSwitch lines directly in the row. With multiple lines it shows an aggregation note — "multiple connections are distributed across the lines; click Edit to change" — plus the latest latency for that line.
Live speedUp/down speed of the app's current active connections, from the core's connection records.
EnabledToggles whether this binding is active.
ActionsEdit and remove. Removal asks for confirmation: "Remove this app binding?".

The Target lines column switches right in the row — no need to open the dialog every time; only aggregated multi-line targets require Edit to re-select. Live speed comes from the core's connection records and shows the app's currently active up/down traffic; it drops to zero when connections close, so it reflects this moment, not cumulative usage. To refresh line latency, use the "refresh lines" style button in the toolbar.

Adding an app binding

Click "Add app binding" to open the dialog; fill in three parts: app, match method and target lines.

FieldNotes
AppEnter a process name (e.g. chrome.exe) or full path (e.g. C:\Games\game.exe); a "Choose program file" button lets you browse for the exe; you can also pick directly from the list of running processes the core has seen making network connections, complete with app icons and window titles.
Match method"By process name (recommended)" or "By full path".
Target linesMulti-select; choosing 2 or more aggregates them automatically for more speed. Options include policy groups, nodes and two fixed entries: "Direct (no proxy)" and "Reject (block connection)".
Aggregation policyAppears only with 2+ lines: "round-robin" (connections spread across lines automatically) or "session-persistent".

There are three ways to fill in the app: type a process name, type a full path, or click "Choose program file" to browse for the exe. If unsure, pick straight from the running-process list (processes the core has seen currently or recently making connections) — icons and window titles make it easier to find the right one. Then the match method decides how the app is recognized: "By process name (recommended)" is shorter and more tolerant of moved or reinstalled programs; "By full path" is more precise.

Target lines and aggregation

Target lines is a multi-select. Choices include policy groups, nodes and two fixed entries: "Direct (no proxy)" and "Reject (block connection)". With 2+ lines the client creates an aggregation group so several lines serve the app at once; with one line, traffic takes just that line. Two or more lines also prompt for an aggregation policy: round-robin spreads connections across lines, while session-persistent keeps a session on one line.

Typical setups

Browser through "Auto Select", games through a "low-latency line", download tools pinned to a single fixed line; or set a chat app to "Reject" to block its connectivity. A few rules of thumb: apps that prize stability get a single line; apps that prize speed get multiple lines aggregated; apps that shouldn't use the proxy get "Direct"; apps that shouldn't be online at all get "Reject".

Routing only affects bound processes

App Routing affects only bound processes; all other traffic still follows the rule list. Bindings depend on the core running — they don't take effect while the core is stopped.

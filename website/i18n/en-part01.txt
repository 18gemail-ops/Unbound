35|Core capabilities
36|Everyday features, made easy to understand
37|Not a pile of features — every step has a clear entry point, a clear status and a plain-language explanation.
38|Subscription management and auto-update
39|Import a subscription with a single link and see usage and expiry right on the card. Set auto-update every 1–24 hours; when an update finishes, the config reloads automatically and a system notification is sent.
40|Per-process routing
41|Send your browser through one line and your games through another. Bind by process name or full path; picking two or more lines forms a load-balance group automatically, with round-robin or session-persistent policies.
42|Chained proxy
43|Assign a front proxy to a restricted node so traffic goes through the relay first. Set it with the chain button on the node card; latency is simply the sum of both hops.
44|Merge override + extension script
45|When you don't want to touch the original subscription, deep-override any config field with a Merge snippet. For bulk edits, the built-in QuickJS engine runs one extension script — rename nodes, add rules, all from a dialog.
46|Desktop floating window
47|Live speed, current node latency and active connections stay on your desktop. 3 sizes, 3 layouts, 7 color themes — with mouse pass-through and drag anywhere.
48|Network rescue kit
49|When the proxy exits unexpectedly and your browser can't open pages, Diagnostics pinpoints the problem first, then one click resets the system proxy and flushes the DNS cache, with an automatic re-check.
50|About configuration
51|Subscriptions, overrides, scripts — three layers, each minding its own business
52|Subscriptions stay pristine and follow upstream updates while your personal changes live in separate files — no overwriting. Swap subscriptions or providers without reconfiguring everything.
53|<b>Profiles</b>: http/https subscription links, drag to reorder, rename, generate a QR code to share with your phone, and view live usage.
54|<b>Merge override</b>: a few lines override fields in the subscription (except app-level settings such as port and mode), deeply merged recursively when the runtime config is generated.
55|<b>Extension script</b>: built-in QuickJS engine — one <code>main(config)</code> function batch-renames nodes and adds or removes rules.
56|<b>Runtime config</b>: app-level fields such as port, secret and mode are injected by the client and never overridden by subscriptions; config changes hot-reload automatically — no manual core restart.
57|<a class="btn btn-ghost" href="./docs/profiles.html">How to use Profiles →</a>
58|App Routing
59|Let every app take its own route
60|No need to switch everything to global for one game. Bind lines by process name or full path; all other traffic keeps following the rules.
61|<b>Easy to pick</b>: choose straight from processes currently using the network, with app icons — no need to remember exe names.
62|<b>Flexible binding</b>: one line goes directly to that group; two or more lines form a load-balance group so multiple lines serve the same app together.
63|<b>Load-balance policies</b>: round-robin spreads connections across lines; session-persistent keeps a session on one line.
64|<b>Visible results</b>: the binding list shows the app's live up/down speed — one glance tells whether it's working.

66|When things go wrong
67|First it tells you what's wrong, then it helps you fix it
68|Diagnostics runs 11 checks in order: core status, port listening, system proxy, DNS resolution, DNS takeover, direct exit, proxy exit, WebRTC leaks, current node, direct GitHub access and config loading. Each check gives a conclusion and a suggested next step.
69|One-click rescue
70|Reset the system proxy and flush the DNS cache — neither needs admin rights and both take effect instantly, enough to fix the most common failure: "browser can't open pages after the proxy exits".
71|Targeted repairs
72|Leftover system proxy settings, DNS servers set to 0.0.0.0, abnormal hosts files, damaged network stacks — each has its own repair button; operations needing admin rights are clearly marked and go through UAC elevation.

108|Features Overview
109|Eleven pages covering everything from setup to troubleshooting
110|The left menu is grouped by usage: set up routes in "Proxy & Routing" first, see what is happening in "Monitoring & Data", and let "Stability & Troubleshooting" handle the unexpected.
111|1. Proxy and routing
112|"Which line does traffic take" splits into three layers: your subscriptions define the available lines, rules decide the default route, and App Routing decides the exceptions.
113|Profiles
114|Supports http/https subscription links; cards can be dragged to reorder, renamed, shared to your phone as a QR code, and usage info refreshed with one click. Multiple subscriptions can be enabled at once, and single nodes can be imported from node links; set an hourly auto-update interval — after an update the config reloads automatically and a system notification is sent, and you can optionally auto-test and switch to the fastest node after updates; usage alerts fire once each when the threshold is reached, expiry nears, or the subscription has expired; before every update the old content is archived automatically, so you can roll back anytime.
115|Proxies
116|Split view: browse by group and subscription source on the left, a node card grid on the right. Supports latency tests for a single node, download speed tests (the original node is restored automatically afterwards), test all, sorting by latency/name, region filters and favorites-only. One click hides timed-out nodes at the top; card columns support 1–4 or auto-fit; with Node health monitoring on, each card also carries a latency trend line (red dots mark failed tests), and with Automatic failover on a current node that keeps failing tests also gets switched away automatically. Switch freely between the list and map views — the map aggregates nodes into dots by region, sized by count and colored by latency; click a dot to drill into that region.
117|App Routing
118|Bind apps to specific lines by process name or full path, picking directly from processes currently using the network. Selecting two or more lines forms a group automatically, with round-robin or session-persistent policies; the list shows each app's live speed.
119|Chained proxy
120|Assign a front proxy to a node so traffic first goes through the relay — ideal for restricted nodes. A chain badge on the node card shows which front proxy is used on hover.
121|Traffic tunnels
122|Forward a local port to a remote target: the core listens locally on the given port and forwards through a chosen exit (proxy group, node or rule-based routing) to the target host — handy for mapping remote intranet services to your machine. Supports TCP / UDP / mixed protocols.
123|Quick rules
124|Right-click any connection on the Connections page and choose "direct for this domain" or "route this domain through a chosen line" — a domain rule is inserted at the very top and takes effect immediately, with no file edits or restarts.
125|Rules and hit statistics
126|Four tabs: Rules, Custom rules, Rule sets and Hit statistics, where you can add, edit, reorder and delete your own rules right in the page — on save they are injected at the very top of the runtime config. Hit stats are sampled every 15 seconds and accumulated to disk — surviving restarts — so you can tell whether a rule is really doing its job.
127|Three ways to proxy traffic — how to choose

144|2. Monitoring and data
145|The pain with proxies is often "not knowing what's happening right now". That's why every status has somewhere to look.
146|Dashboard
147|Core status, version, memory usage and uptime; total up/down traffic and active connections; a live traffic chart. You can also switch each proxy group's current node right on the Dashboard.
148|Connections
149|The detail view lists host, process, destination, matched rule, chain and live speed for each connection; the aggregated view groups connection counts by domain. Right-click to create a quick rule for a domain or copy the domain, destination address or process path.
150|Traffic
151|Records daily up/down usage with 7-day / 30-day / 90-day / all-time views, plus a trend chart and a daily detail table; a Node traffic panel groups traffic by the exit node each connection finally leaves through (direct traffic is recorded as DIRECT), so you can see how much each line has used, with a one-click stats reset. Data is continuously persisted and survives restarts.
152|Logs
153|Core logs and app logs shown on one screen; app logs carry a <code>[Unbound link]</code> prefix for easy distinction. Filter by Debug / Info / Warning / Error. Logs are also written to <code>logs\app.log</code> with automatic rotation and expiry cleanup.
154|Desktop floating window
155|Live speed, current node latency, active connections, today's traffic and proxy status on your desktop. 3 sizes, 3 layouts, 7 color themes, adjustable opacity, mouse pass-through and automatically remembered position.
156|System tray
157|The tray icon switches between three states with the proxy status (normal / system proxy / TUN), and each state can be replaced with your own PNG icon. Right-click opens a quick panel to toggle the system proxy or TUN, see speed or open the main window without launching the full app. Click the "node" or "group" row and a standalone node picker pops up beside it: browse by group, click to switch.
158|3. System integration
159|Take over what belongs to the system; keep local what belongs to the machine.
160|System proxy and TUN
161|One click writes or restores Windows Internet settings; with "Network environment" on, the system proxy and mode also switch automatically by Wi-Fi name (e.g. on at home, off at the office). TUN takes over all traffic at the network layer through a virtual adapter, with Mixed / Gvisor / System stacks to choose from. When admin rights are needed, a UAC prompt guides the elevation. If Store apps can't reach the local proxy due to the loopback restriction, the UWP App Tool lifts it with one click.
162|DNS and LAN
163|Custom DNS servers (including fallback DNS and static Hosts) can override the subscription's settings, with optional fake-ip acceleration; enabling "allow LAN" lets phones, tablets and other devices on the same subnet use the local proxy directly. The Share to phone button on the same row then shows a QR code — set the phone's Wi-Fi manual proxy as prompted.
164|Built-in web dashboard
165|The built-in MetaCubeXD dashboard downloads and hosts itself on first open at <code>http://127.0.0.1:9090/ui/</code>; with LAN enabled, an address for other devices to access the dashboard is also shown.
166|Global shortcuts
167|Defaults: <code>Ctrl+Shift+P</code> toggles the system proxy, <code>Ctrl+Shift+T</code> toggles TUN, <code>Ctrl+Shift+U</code> shows the main window, <code>Ctrl+Shift+O</code> toggles the floating window and <code>Ctrl+Shift+M</code> switches the proxy mode. "Update all subscriptions" and "Restart core" can be recorded separately — all shortcuts are customizable or resettable to default.
168|Global command palette
170|Launch at startup and single instance
171|Optionally run at startup; the app is single-instance, so launching it again brings up the existing window — no two cores fighting over ports. Closing the main window minimizes to the tray instead of exiting. On a fresh install, the first launch opens a four-step guide that walks you through importing a subscription and recommended settings.
172|Themes and appearance
173|Dark / light / follow-system modes with instant switching; brand color, secondary color, text color, semantic colors, UI font and custom CSS are all adjustable. The flat design uses black primary buttons and restrained semantic colors — blue for in-progress, green for normal, amber for pending, red for errors.
174|Configuration capabilities
175|For those who don't want to touch configs — and those who do
176|Subscriptions stay pristine while your changes live in a separate file; the two merge only when the runtime config is generated — meaning subscription updates never overwrite your personal settings.
177|<b>Merge override</b>: a few lines of YAML override fields in the subscription (app-level settings such as port and mode are handled by the client), deeply merged recursively.
178|<b>Extension script</b>: built-in QuickJS — one <code>main(config)</code> function batch-renames nodes and adds or removes rules.
179|<b>Node Cleanup</b>: filter nodes by keyword and batch-rename them by rules (with common prefixes/suffixes), rewriting references in proxy groups and rules to match — preview before enabling.
180|<b>App-level settings injection</b>: fields such as port, control secret and mode are written by the client and never overridden by subscription content.
181|<b>Config hot reload</b>: switching nodes, changing ports or DNS applies automatically without interrupting existing connections.
182|<b>Atomic writes</b>: the runtime config is written to a temp file first, then renamed, so the core never reads a half-written file.
183|<b>Config snapshots</b>: before each runtime config is generated the previous version is archived automatically (the latest 10 are kept); if the core won't start, roll back to the last working version in one click — an emergency fallback.
184|Backup and restore
185|Export settings, subscriptions, Merge config and the core version into a single JSON file; after switching computers or reinstalling, import it with one click under Settings → Maintenance to restore everything. "Export diagnostics" packages versions, settings, config and recent logs into a ZIP (sensitive fields redacted) to make reporting issues easier.
186|One-click core update
187|Settings → Maintenance → Core update checks for and fetches new core versions, replacing the current one automatically after download — no manual file handling.
188|Core watchdog
189|Automatically restarts the core if it exits unexpectedly, with debounce protection: repeated crashes in a short time won't cause an infinite restart loop — they're faithfully recorded in Logs instead.
190|4. Stability and troubleshooting
191|The worst part of proxy trouble is not knowing where the problem is. So diagnosis and repair are split into two steps.
192|11 network checks
193|Core status, port listening, system proxy, DNS resolution, DNS takeover, direct exit, proxy exit, WebRTC leaks, current node, direct GitHub access and config loading. Each gives a conclusion, and abnormal items come with suggestions.
194|Network rescue kit
195|For five classes of problems — leftover system proxy settings, DNS resolution failures, rewritten DNS servers, abnormal hosts files and damaged network stacks — each is detected with a matching repair button and an automatic re-check afterwards.
196|Unlock Test
197|Checks 18 services through the current exit — streaming such as Netflix and Disney+, AI services such as ChatGPT and Claude, and China-side platforms such as Bilibili — and reports one of four states with a note: Unlocked / Partial / Blocked / Failed. Switch the exit node on the page itself to pick a route and retest right away.
198|A note on privileges
199|In the one-click rescue, resetting the system proxy and flushing the DNS cache need no admin rights and are always available; only resetting DNS servers, restoring the hosts file and resetting the network stack require UAC elevation, clearly marked in the UI.

322|FAQ
323|Start here — chances are you'll find your answer
324|Installation failures, connection issues, "where is that switch" — the guide covers them all; this page gathers the most frequently asked questions.
325|About the software itself
326|How does Unbound link relate to Clash-based clients?
327|Unbound link is a Windows desktop client whose networking power comes entirely from the <b>mihomo core</b> (the successor of the Clash Meta line) — it implements no proxy protocols itself. Its job is subscription management, runtime config generation, core lifecycle and supervision, and observing and controlling the core through its API.
328|Do I need to download and place the core myself?
329|No. The core (mihomo) and TUN driver ship with the installer, and the client starts and stops them. You don't edit config files by hand either — the runtime config is generated by the client from your subscription and settings.
330|The core itself can be checked and updated under Settings → Maintenance → Core update.
331|Is macOS or Linux supported?
332|Currently only 64-bit Windows 10 / 11. Some features (system proxy writes, the TUN virtual adapter, the tray and UAC elevation) rely on Windows capabilities.
333|Where do I get a subscription?
334|Subscriptions come from your own provider — the client bundles none and resells none. Once you have a link like <code>https://…</code>, paste it into Profiles → Add subscription.
335|Can I import multiple subscriptions?
336|You can import and keep multiple subscriptions, and drag cards to reorder them. Each subscription has its own enable switch — several can be on at once: the first enabled subscription supplies the base config (port / DNS / mode), while the others merge in their nodes, proxy groups and rules; the effective order follows the list from top to bottom. Changing what's enabled regenerates the runtime config.
337|Making the proxy work
338|The system proxy is on — why do some apps still bypass it?
339|That's the inherent limitation of system proxies: only programs that read Windows Internet settings (browsers, most desktop software) use it. Games, some command-line tools and apps with their own network stack ignore this setting.
340|Two fixes: enable <b>TUN mode</b> (the virtual adapter takes over all traffic at the network layer; admin rights required), or bind the process to a chosen line with <b>App Routing</b>.
341|Apps from the Microsoft Store can't reach the network — what should I do?
342|Windows blocks Store apps from accessing local addresses (<code>127.0.0.1</code>) by default, so they can't use the local proxy directly — the app shows no connectivity, spinning forever.
343|Go to Settings → Tools → UWP App Tool → Manage apps and flip the switch to lift the loopback restriction; this needs admin rights — if it fails, restart the app as administrator and try again.
344|System proxy, TUN mode or App Routing — which should I use?
345|<b>System proxy</b>: covers browsers and most software, needs no extra privileges — the everyday first choice.
346|<b>TUN mode</b>: covers all traffic, including apps that ignore the system proxy; requires admin rights.
347|<b>App Routing</b>: affects only bound processes — for singling out individual apps onto dedicated lines.
348|All three can be enabled at the same time without conflict.
349|What's the difference between Rule, Global and Direct modes?
350|<b>Rule</b> decides each connection's path from the subscription and your own rules — the everyday mode; <b>Global</b> ignores rules and sends everything through the selected exit; <b>Direct</b> bypasses the proxy entirely.
351|Switch under Settings → Network → Mode. Note: in Global or Direct mode, rules in the rule list no longer take effect.
352|Quick rules vs. subscription rules — which wins?
353|Quick rules. Domain rules you create by right-clicking on the Connections page are inserted at the very top of the rule list, so they match before subscription rules and take effect immediately — no core restart needed.
354|All nodes show as timed out — what now?
355|Check in order: ① On the Proxies page click "Test all" for the latest latencies; ② On the Profiles page click "Traffic" on the card to refresh usage info and confirm the subscription hasn't expired; ③ Click "Update" to re-fetch the subscription; ④ Check the "direct exit / proxy exit" and "current node" conclusions in Diagnostics.
356|For more scenarios see <a href="./docs/troubleshooting.html">Troubleshooting</a>.
357|Does switching nodes drop existing connections?
358|Switching nodes or changing DNS/ports applies to the core via hot reload — the core process itself is not restarted. Connections already in flight may be re-established because the exit changed; that's normal proxy behavior.
359|Privileges and data
360|Why do some operations require admin rights?
361|Operations that modify system-level settings require admin rights: enabling TUN mode, resetting DNS servers, restoring the hosts file and resetting the network stack. The client marks them clearly in the UI and elevates via UAC when executed — never silently.
362|Resetting the system proxy and flushing the DNS cache in one-click rescue need no admin rights and are always available.
363|Does the software collect or upload my data?
364|No account required, no telemetry. Settings, subscriptions, statistics and logs all live in the local data directory <code>%APPDATA%\com.unboundlink.desktop</code>.
365|The app makes only three kinds of outbound requests: fetching your subscription links, checking for and downloading core updates, and probe requests during Diagnostics and speed tests (e.g., 204 check endpoints and your own nodes).
366|Switching computers or reinstalling — how do I keep my setup?
367|Settings → Maintenance → Backup and restore → Export backup produces a JSON file with your settings, subscriptions, Merge config and core version. Install in the new environment and click "Import backup" to restore (this overwrites current settings and subscriptions).
368|I want to report a problem — what information helps most?
369|Settings → Maintenance → Backup and restore → Export diagnostics produces a ZIP with app and core versions, current settings, runtime config and recent logs — secrets and other sensitive fields are redacted automatically, so you can attach it directly to your report.
370|After uninstalling, my browser can't open pages?
371|That means the system proxy was still on at uninstall time and the browser is still pointing at the local proxy port. Fix: reinstall and click "One-click rescue" in Diagnostics → Network rescue (reset system proxy + flush DNS cache), or clear the proxy server in Windows Internet Options → Connections → LAN settings.
372|In the future, turn off the system proxy under Settings → System → System proxy before uninstalling.
373|Will uninstalling delete my settings and subscriptions?
374|No. The uninstaller only removes program files; the data directory stays. To clean up completely, delete <code>%APPDATA%\com.unboundlink.desktop</code> manually.
375|Usage details
376|Which ports are used by default? What if they're taken?
377|The default mixed proxy port is <code>7890</code> and the control API port is <code>9090</code>. The "port listening" check in Diagnostics tells you whether the ports are properly listened on or taken by another program. Change them under Settings → Network → Ports and mode; the core restarts automatically after changes.
378|Why does the download speed test run only about 10 seconds — and switch nodes temporarily?
379|The gauge icon on a node card runs a download speed test; reflecting real bandwidth takes actual downloading, hence roughly 10 seconds. The test temporarily switches the exit to that node and restores the previously selected node when done. Results are cleared automatically after about 10 minutes so stale data doesn't mislead.
380|Why do the logs have two sources?
381|Logs from the core itself (connections, rule matching, etc.) come over the core's live channel; the client's own operation logs (subscription updates, config reloads, core start/stop, etc.) carry a <code>[Unbound link]</code> prefix. Both appear together in time order on the Logs page, and level filters apply to both.
382|Where does the app go when I close the window?
383|By default "minimize to tray on close" is on — the close button only hides the window and the proxy keeps running. Right-click the tray icon to reopen the main window or exit completely. This behavior can be changed under Settings → System → Tray and watchdog.
384|How do I customize the floating window — and will it block mouse clicks?
385|The floating window offers 3 sizes, 3 layouts (card / capsule / gauge) and 7 color themes; latency, connection count, traffic chart, today's traffic and proxy status can each be toggled, and opacity adjusted. If clicks bother you, enable "mouse pass-through" under Settings → System → Tray and watchdog.
386|Are there keyboard shortcuts?
387|Five global shortcuts by default: <code>Ctrl+Shift+P</code> toggles the system proxy, <code>Ctrl+Shift+T</code> toggles TUN mode, <code>Ctrl+Shift+U</code> shows the main window, <code>Ctrl+Shift+O</code> toggles the traffic floating window and <code>Ctrl+Shift+M</code> cycles the proxy mode (Rule → Global → Direct). "Update all subscriptions" and "Restart core" are unbound by default and can be recorded. Find them under Settings → System → Global shortcuts; record your own or reset to defaults.
388|Still stuck?
389|Check the <a href="./docs/troubleshooting.html">Troubleshooting</a> and <a href="./docs/diagnose.html">Diagnostics</a> chapters of the guide first; if that doesn't help, open an issue in the repository — including error lines from the Logs page and the Diagnostics conclusions speeds up the investigation.

606|App Routing
607|Route different apps through different lines: bind your browser, games and download tools to suitable lines, each independent of the others.
608|The page subtitle says it: route different apps through different lines. The "Enable App Routing" master switch sits at the top, off by default, with an "Add app binding" button above the table. The master switch gates this whole page — bindings you add below only take effect once it's on. Each binding connects one app to one or more lines, after which that app's traffic follows the bound lines.
609|The binding table
610|All bindings are listed in a table, one binding rule per row.
611|Column
612|Meaning
613|<b>App</b>
614|Shows the icon and name / process name.
615|<b>Target lines</b>
616|Switch lines directly in the row. With multiple lines it shows an aggregation note — "multiple connections are distributed across the lines; click Edit to change" — plus the latest latency for that line.
617|<b>Live speed</b>
618|Up/down speed of the app's current active connections, from the core's connection records.
619|<b>Enabled</b>

624|Adding an app binding
625|Click "Add app binding" to open the dialog; fill in three parts: app, match method and target lines.
626|Field
627|Notes
628|<b>App</b>
629|Enter a process name (e.g. <code>chrome.exe</code>) or full path (e.g. <code>C:\Games\game.exe</code>); a "Choose program file" button lets you browse for the exe; you can also pick directly from the list of running processes the core has seen making network connections, complete with app icons and window titles.
630|<b>Match method</b>
631|"By process name (recommended)" or "By full path".
632|<b>Target lines</b>
633|Multi-select; choosing 2 or more aggregates them automatically for more speed. Options include policy groups, nodes and two fixed entries: "Direct (no proxy)" and "Reject (block connection)".
634|<b>Aggregation policy</b>
635|Appears only with 2+ lines: "round-robin" (connections spread across lines automatically) or "session-persistent".
636|There are three ways to fill in the app: type a process name, type a full path, or click "Choose program file" to browse for the exe. If unsure, pick straight from the running-process list (processes the core has seen currently or recently making connections) — icons and window titles make it easier to find the right one. Then the match method decides how the app is recognized: "By process name (recommended)" is shorter and more tolerant of moved or reinstalled programs; "By full path" is more precise.
637|Target lines and aggregation
638|Target lines is a multi-select. Choices include policy groups, nodes and two fixed entries: "Direct (no proxy)" and "Reject (block connection)". With 2+ lines the client creates an aggregation group so several lines serve the app at once; with one line, traffic takes just that line. Two or more lines also prompt for an aggregation policy: round-robin spreads connections across lines, while session-persistent keeps a session on one line.

653|Typical setups
654|Browser through "Auto Select", games through a "low-latency line", download tools pinned to a single fixed line; or set a chat app to "Reject" to block its connectivity. A few rules of thumb: apps that prize stability get a single line; apps that prize speed get multiple lines aggregated; apps that shouldn't use the proxy get "Direct"; apps that shouldn't be online at all get "Reject".

771|Diagnostics
772|Diagnostics checks the core, ports, system proxy, DNS, exits and leaks in one pass, with a conclusion and suggestion for each item, plus the network rescue kit.
773|What this page solves
774|When pages won't load or the proxy seems ineffective, no need to guess. 777|Check
778|What it inspects
779|<b>Core status</b>
780|Whether the core is running, its version, and whether it's elevated.
781|<b>Port listening</b>
782|Whether the mixed and control ports are taken by other programs.
783|<b>System proxy</b>
784|Whether the system proxy is on and points at the local mixed port.
785|<b>DNS resolution</b>

789|<b>Direct exit</b>

801|Network rescue kit
802|The "Network rescue kit" section sits below, described as: "When the proxy exits unexpectedly, DNS breaks or pages won't load: detect first to locate the problem, then repair as prompted." It offers two buttons: "One-click rescue" and "Start check / Re-check".

Detect first to locate the problem, then decide whether to use one-click rescue.
804|Outage-specific checks
805|The dedicated checks cover five classes of problems, each with a matching repair button:
806|Problem
807|Symptom
808|Repair button
809|<b>Leftover system proxy</b>

811|Reset system proxy
812|<b>DNS resolution failure</b>

847|Term
848|Meaning
849|<b>Core</b>
850|The program doing the real work (mihomo). It's installed with the app; the client starts, supervises and stops it — you never install or configure it separately.

1083|Manual nodes live in the data directory and merge into a proxy group of the same name when the runtime config is generated (default group name: "Manual Nodes"). Remove imported nodes one by one on the card; changes save immediately and hot-reload the config.
1084|Global override config (Merge)
1085|At the bottom sits the "Global override config" card with a <b>Merge</b> tag. Open it and write a YAML snippet — when the runtime config is generated it's <b>deeply merged recursively</b> with the subscription to override its fields (app-level settings such as port, control secret and mode are written by the client — writing them here has no effect; change them under Settings → Network). Saving shows "Merge config saved and applied".
1086|Global extension script (Script)
1087|Next to it, the "Global extension script" card with a <b>Script</b> tag. Open it and write JavaScript implementing <code>function main(config){ … return config }</code>. The client runs it on the built-in <b>QuickJS</b> engine to batch-rename nodes, add or remove rules and more. Saving shows "Extension script saved and applied". A sample script using regex to strip ads from node names comes built in.
1088|Auto-update
1089|The auto-update interval is set under Settings → Maintenance → Subscription, in hours, <b>0 means off</b> (off by default). Once enabled, every subscription in the list updates on schedule in the background; when done, the config reloads automatically and a system notification is sent.
1090|Two subscription-linked switches live in the same place: "Auto-optimize after update" is off by default — once enabled, every time a subscription update finishes and the config reloads, it tests the main proxy group and switches the current node to the lowest-latency one; "Profile usage alerts" is on by default and sends a system notification when used traffic reaches the threshold, remaining days run low or the subscription has expired, each tier firing only once. Both rely on the traffic and expiry info provided by the subscription source.
1091|If updates fail, check the network first
1092|Failed updates usually mean a dead URL or a broken connection. Check the network in Diagnostics, then come back and retry "Update".

1180|Rules
1181|The Rules page answers "which line does which traffic take": it lists the rules in effect, the rule sets your subscription references, and how often each rule is actually hit.
1182|Four tabs
1183|Four tabs at the top: <b>Rules</b>, <b>Custom rules</b>, <b>Rule sets</b> and <b>Hit statistics</b> — different facets of the same rule set: "what rules exist", "which extra rules I want", "where they come from" and "how well they're used". Switch tabs to view each without leaving the page.
1184|Rules
1185|The default first tab lists every rule in the current runtime config. Data comes from the exact config the core reads — your subscription and overrides combined. Four columns:
1186|Column
1187|Meaning
1188|<b>Type</b>
1189|The match type, e.g. DOMAIN-SUFFIX, GEOIP and so on.
1190|<b>Match</b>
1191|The domain, IP range or region this rule matches.
1192|<b>Policy (exit)</b>
1193|Where matched traffic exits — usually a proxy group, a node name, or a built-in policy like DIRECT or REJECT.
1194|<b>Hits</b>
1195|How many times this rule has been hit in total.
1196|Rule counts are often large, so filtering and search sit above: filter by type or search the match content by keyword. Long results paginate automatically to help you find a specific rule.
1197|Custom rules
1198|The Custom rules tab is a visual editor: add, edit and reorder your own routing rules without hand-writing config files. On Save & apply they are injected at the <b>very top</b> of the runtime rules in list order, outranking quick rules and subscription rules.
1199|Editing is draft-style: changes stay on the page, a Discard changes button and an unsaved-changes note appear, and nothing is written until you click Save & apply, which hot-reloads the core; Discard changes restores the saved state. The table shows all rules in the draft with six columns: <b>#</b>, <b>Type</b>, <b>Match</b>, <b>Policy</b>, <b>Extra</b> and <b>Actions</b>. Each row has four buttons: <b>Move up</b>, <b>Move down</b>, <b>Edit</b> and <b>Delete</b>; higher rows have higher priority, and Move up on the first row and Move down on the last are disabled.
1200|Click Add rule or a row's Edit button to open a form with four fields:
1201|Field
1202|Notes
1203|<b>Rule type</b>
1204|e.g. DOMAIN-SUFFIX, GEOSITE, IP-CIDR; type freely or pick from the common suggestions — values are upper-cased automatically.
1205|<b>Match</b>
1206|The domain, IP range or region to match. Not needed for the MATCH type.
1207|<b>Target</b>
1208|The exit on a hit: DIRECT, REJECT, or a proxy group / node name from the running core (pick from the suggestions).

1210|Rule types are limited to upper-case letters, digits and hyphens, and Match / Target must not contain commas or line breaks; if any rule fails validation the whole save is rejected with the offending row number. Up to 200 custom rules.

1212|Custom rules go to the very top of the rule list, and matching runs top to bottom — the first hit wins. Put a MATCH rule first and nothing below it will ever match.

1219|<b>Type</b>

1224|How many rules the set contains.
1225|<b>Updated</b>
1226|When the rule set was last updated.
1227|Hit statistics
1228|The Hit statistics tab presents rules by actual usage in four columns: <b>Type</b>, <b>Match</b>, <b>Exit</b> and <b>Hits</b>, so you can see which rules really pull their weight.
1229|The client samples connection records <b>every 15 seconds</b> while the core runs and accumulates them to disk, so right after launch it may show "No statistics yet (sampled every 15 seconds while the core runs)" — data trickles in shortly after. Statistics are persisted and survive restarts.
1230|Route simulator
1231|The toolbar on the Rules page has a Route simulator button: type a domain, IP or process name and it replays locally which rule would match and what its policy is. No running core is required — very handy for working out why a site went the way it did.
1232|Two input modes are supported: <b>Domain / IP</b> matches domain- and IP-based rules; <b>App process</b> matches process rules (e.g. chrome.exe). Results show the matched rule number, its text and policy; if the policy is a proxy group, the group's current exit node is resolved too.
1233|A few rules cannot be decided locally (those relying on GeoSite / GeoIP data, regex, or pending domain resolution); the simulator lists them as skipped instead of giving a wrong answer, and malformed input gets its own hint. Every decision is based on the current runtime config — the same rules the core actually uses.
1234|Rule priority
1235|Rules match top to bottom; the first hit wins. In the runtime config the order is: <b>custom rules</b> (arranged in the Rules page editor) → <b>quick rules</b> (right-click on the <a href="./connections.html">Connections</a> page) → subscription rules. Both in-app sources sit above subscription rules, with custom rules highest. <a href="./apps.html">App routing</a> bindings match by process and also apply at config generation time.
1236|Changed rules but nothing changed?
1237|First check the mode is "Rule": Settings → Network → Mode. In Global mode all traffic takes one exit and rules have no effect.

1550|What this page solves
1551|It answers "how much traffic did I use these days". All data comes from the local core — no server collects it; what you see is this computer's actual usage.

1559|What to look at and how

1597|Troubleshooting
1598|Common problems below follow Symptom → Cause → Fix, each with concrete steps — just work through them in order.
1599|Pages won't load / no network
1600|<b>Symptom</b>: the browser can't open any page.
1601|<b>Cause</b>: leftover system proxy settings, a bad DNS cache or an unhealthy network stack.
1602|<b>Fix</b>: open Diagnostics and check the first few results; then run "One-click rescue" in the network rescue kit (reset system proxy + flush DNS cache, no admin rights needed). If that still doesn't help, follow the on-screen prompt to reset the network stack — that requires admin rights and takes effect after a reboot.
1603|The proxy isn't taking effect
1604|<b>Symptom</b>: the internet works, but traffic doesn't go through the proxy.
1605|<b>Cause</b>: the mode was switched to Global or Direct; the system proxy is off; the core isn't running.
1606|<b>Fix</b>: open Settings → Network and check the mode is "Rule" (choosing "Global" or "Direct" changes behavior); open Settings → System → System proxy and check it's on; then confirm the core is running via the core status on the Dashboard or in Diagnostics.
1607|Some apps bypass the proxy
1608|<b>Symptom</b>: the browser works, but some programs don't use the proxy — and apps from the Microsoft Store can't open pages at all.
1609|<b>Cause</b>: this is the inherent limitation of system proxies — some programs don't read the setting; Store apps are also subject to the Windows loopback restriction, which blocks access to the local address (<code>127.0.0.1</code>) by default.
1610|<b>Fix</b>: for Store apps, open Settings → Tools → UWP app tool and flip the switch to lift the loopback restriction (needs admin rights); for other programs switch to TUN mode (see Settings → Network → TUN mode), or bind the process to a chosen line with App Routing.
1611|All nodes time out
1612|<b>Symptom</b>: every node tests as timed out.
1613|<b>Cause</b>: the nodes are temporarily unavailable, or the subscription has expired or is stale.
1614|<b>Fix</b>: first click "Test all" on the Proxies page; check whether the subscription has expired and click the "Traffic" button on its card under Profiles to refresh the info; then check the "direct exit / proxy exit" and "current node" conclusions in Diagnostics; you can also click "Update" for the subscription on the Profiles page. To clear useless timed-out nodes, turn on the "Hide timed-out" switch at the top of the Proxies page.
1615|Port already in use
1616|<b>Symptom</b>: the core can't listen; a port conflict is reported.
1617|<b>Cause</b>: the default port is taken by another program.
1618|<b>Fix</b>: the "port listening" check in Diagnostics shows which port is taken; change the mixed proxy port or the control port under Settings → Network → Ports and mode — the core restarts automatically after changes.
1619|Subscription update fails
1620|<b>Symptom</b>: clicking "Update" changes nothing.
1621|<b>Cause</b>: the subscription URL is unreachable, or the current network is down.
1622|<b>Fix</b>: confirm the subscription URL is reachable; check the error lines under Logs; if the network is down, use Diagnostics to locate the problem first.
1623|TUN won't enable / "Not elevated" warning
1624|<b>Symptom</b>: turning on "Enable TUN" has no effect, and the privilege badge shows an orange "Not elevated".
1625|<b>Cause</b>: the current process lacks admin rights, or the install directory is in use.
1626|<b>Fix</b>: go to Settings → Network → TUN mode and click "Restart as administrator", confirm the UAC prompt and retry; also make sure the install directory isn't in use.
1627|Settings changed but nothing happened
1628|<b>Symptom</b>: changing a setting doesn't change the behavior.
1629|<b>Cause</b>: core-related changes need a reload or restart of the core; or config generation failed.
1630|<b>Fix</b>: core-related changes (ports, TUN, DNS) reload or restart the core automatically; if nothing changes, check Logs for config errors and, if needed, check the Merge override or extension script under Profiles — a syntax error makes config generation fail.
1631|Data and backup
1632|<b>Symptom</b>: you need to migrate to a new machine or reinstall Windows.
1633|<b>Cause</b>: the data directory lives under the user folder on the system drive and is lost on reinstall.
1634|<b>Fix</b>: the data directory is <code>%APPDATA%\com.unboundlink.desktop</code>. Before migrating or reinstalling, open Settings → Maintenance → Backup and restore → Export backup, then restore it in the new environment with "Import backup". When you need help troubleshooting, click "Export diagnostics" first and attach the ZIP to your report.
1635|The core won't start
1636|<b>Symptom</b>: the core status never shows Running.
1637|<b>Cause</b>: the install directory is incomplete — the core sidecar is missing or damaged.
1638|<b>Fix</b>: make sure the install directory is complete (the core ships as a sidecar program with the installer); check Logs for errors; go to Settings → Maintenance → Core update and click "Check for updates" to re-fetch the core.

1641|Check Logs for errors.
1642|Run Diagnostics and check the first 4 items.
1643|Use the network rescue kit.
1644|Check the mode and the system proxy.
1645|Check whether the subscription needs updating.
1646|Check for port conflicts.
1647|If the problem is hard to pin down, click Settings → Maintenance → Backup and restore → Export diagnostics and attach the ZIP to your report.

1661|Unlock Test
1662|Unlock Test visits 18 popular services through the current exit and reports Unlocked / Partial / Blocked / Failed for each, so you can tell whether this route can stream and use AI tools.
1663|What this page solves
1664|"I switched to a new node — can I still watch Netflix?" "ChatGPT suddenly won't sign in?" Questions like these do not need a website-by-website check. This page tests all 18 services in one pass and reports the results without delay. Requests leave through the local mixed port — the same proxy path your daily traffic takes — so what you see is the real result of the <b>current exit node</b>; switch to another route and the outcome can be completely different.
1665|How to use it
1666|<b>Pick the exit</b>: the "Exit node" row at the top has two dropdowns — pick a group, then a node; you can switch right here, and each node shows its latency;
1667|<b>Start a test</b>: click "Test all" at the top right to check all 18 in parallel, or click the refresh icon on a single card to test just that service;
1668|<b>Read the results</b>: the subtitle summarizes "Unlocked N · Partial N · Tested N/18" in real time, and each card shows a status badge and a short note.
1669|What the states mean
1670|Status
1671|Meaning
1672|<b>Not tested</b>
1673|Not tested yet. Click the refresh icon on the card to run a single check.
1674|<b>Unlocked</b>
1675|The service is fully available through the current exit.
1676|<b>Partial</b>
1677|Reachable, but with limited content — the classic case is Netflix showing only its own productions.
1678|<b>Blocked</b>
1679|Clearly unavailable; the detail line shows the HTTP status code or the region notice.
1680|<b>Failed</b>
1681|The request itself did not complete (timeout, proxy unreachable, etc.) — <b>this does not mean the service is unavailable</b>. Check the core and node status first, then test again.
1682|How the checks work
1683|Every check sends requests through the local mixed port with a browser User-Agent and a 12-second timeout. Each service is judged differently:
1684|<b>Netflix</b>: two titles are cross-checked — an original series first, and only if it returns 200, a non-original title. Both reachable means Unlocked; only the original means Partial; otherwise Blocked.
1685|<b>Disney+ / Prime Video / Spotify / TikTok</b>: the home page loads and shows no "not available in your region" notice — Unlocked.
1686|<b>Hulu / HBO Max</b>: a redirect to a region notice page, or restricted-content text on the page, means Blocked.
1687|<b>ChatGPT Web</b>: a 403 response means the region is unsupported; <b>ChatGPT iOS</b> probes a long-stable mobile status endpoint instead.
1688|<b>Bilibili</b>: an in-site API reports how Bilibili sees the exit region — mainland China gets the full catalogue, while Hong Kong, Macao, Taiwan and overseas regions are partially restricted.
1689|<b>Claude / Copilot / Gemini / X / iQIYI / Tencent Video / NetEase Cloud Music</b>: home page reachability; region limits show up as a 403 or a redirect to a notice page.
